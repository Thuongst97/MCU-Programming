Bare Metal vs RTOS: FreeRTOS on Cortex-M3

A super-loop gets you a long way, until several jobs with different deadlines have to share one CPU. This module shows when an RTOS starts to pay off, how the Cortex-M3 switches between tasks in hardware and software, and how to use FreeRTOS on the Blue Pill without the classic priority and stack traps.

⏱ 50 min read🎯 Intermediate📂 examples/10-freertos-basics

14.1When you need an RTOS

A super-loop (for (;;) { a(); b(); c(); }) plus interrupts is the right design for most small programs: you can see the whole schedule in one screen and nothing switches behind your back. It stops scaling when:

  • jobs have different deadlines: a 10 ms control loop must not wait for a 50 ms display refresh;
  • a job has to wait in the middle (for a reply, a flash erase, a bus) and you end up turning every function into a hand-written state machine;
  • several modules are written by different people and nobody can reason about the total loop time any more.

An RTOS lets each job be written as a plain sequential function, a task, with its own stack. A preemptive scheduler always runs the highest-priority task that is ready; when it blocks (waiting for time, a queue or a semaphore), the next one runs. The price: RAM for every stack, a few microseconds per switch, and a new class of bugs (races, deadlocks, priority inversion) that this module teaches you to avoid.

🎭
Analogy

An RTOS is air-traffic control for planes sharing one runway. Each pilot (task) flies their own route; the controller (scheduler) decides who may use the runway now, by priority. A plane circling in a holding pattern (blocked task) costs no runway time.

14.2A context switch, step by step

The Cortex-M3 was designed with an RTOS in mind (PM0056 §2.3, ARMv7-M ARM B1.5). Three features do the heavy lifting:

  • Two stack pointers: tasks run in Thread mode on the process stack (PSP); exceptions and the kernel use the main stack (MSP).
  • Hardware stacking: on exception entry the core pushes eight registers (R0–R3, R12, LR, PC, xPSR) onto the active stack by itself.
  • PendSV: an exception software can make pending, set to the lowest priority, so the switch happens only after every other interrupt has finished.
ℹ️
Why not switch inside SysTick?

If the tick interrupted another ISR, switching tasks there would return to a different task with the first ISR only half done. Deferring the switch to the lowest-priority PendSV guarantees that no ISR is in progress when the stacks are exchanged.

14.3Task states (interactive)

Every FreeRTOS task is in one of four states. Drive the machine with the event buttons; the descriptions name the API calls that cause each transition.

Only one task is Running at a time on a single core. A task that waits for something is Blocked, usually with a timeout, and uses no CPU at all. That is the main difference to a super-loop's busy polling.

14.4Porting FreeRTOS to the Blue Pill

FreeRTOS needs three things from the chip: a tick (SysTick), the PendSV and SVC exceptions, and a way to mask interrupts. The Cortex-M3 port in third_party/freertos_kernel/portable/GCC/ARM_CM3 provides all of them; we only write FreeRTOSConfig.h and map the handler names onto our vector table.

⚠️
Priority numbers run in opposite directions

On the NVIC, lower numbers are more urgent (0 is the highest). In FreeRTOS task priorities, higher numbers are more urgent. And the STM32F1 implements only the top 4 bits of each 8-bit NVIC priority, so priority 5 is written as 5 << 4 = 0x50. CMSIS NVIC_SetPriority() does the shift for you; the config…PRIORITY macros in FreeRTOSConfig.h must contain the shifted value.

The kernel masks interrupts with BASEPRI, not by disabling them all. With our setting, NVIC priorities 0–4 are never masked by the kernel (lowest latency), but they must not call any FreeRTOS function. Priorities 5–15 may call …FromISR functions.

⚠️
Priority inversion

A low-priority task holds the UART; a high-priority task wants it and blocks; a medium-priority task that needs neither now runs for as long as it likes, so the high-priority task waits for the medium one. A FreeRTOS mutex fixes this by temporarily raising the holder to the waiter's priority (priority inheritance). A binary semaphore used as a lock does not, which is why locks are always mutexes.

14.6ISR rules: FromISR APIs

An interrupt handler is not a task: it cannot block. FreeRTOS therefore has a separate …FromISR variant of every function an ISR may need. They never wait, and they tell you whether a higher-priority task became ready so you can switch on the way out.

  • Only …FromISR functions in an ISR, and only from an interrupt whose NVIC priority is at or below configMAX_SYSCALL_INTERRUPT_PRIORITY (numerically ≥ 5 here). With configASSERT defined, the port checks this and stops at the assertion instead of corrupting the kernel's lists.
  • Keep ISRs short: acknowledge the hardware, hand the work to a task, leave.
  • Set every interrupt's priority explicitly. After reset all NVIC priorities are 0, the most urgent level, which is above the syscall limit.

14.7Stack sizing and overflow detection

Each task's stack is an array you size. Too small and the task silently overwrites whatever lies next to it in RAM; too large and you run out of the 20 KB. Measure instead of guessing:

  • uxTaskGetStackHighWaterMark() returns the smallest amount of free stack a task has ever had, in words. Example 10's monitor task prints it every 2 s. Keep a margin of at least 25 % after exercising every code path.
  • configCHECK_FOR_STACK_OVERFLOW = 2 fills each stack with a known pattern and checks its end at every context switch; on a hit it calls the hook below. It catches most overflows, not all (a large local array can jump past the checked bytes).
💡
printf is a stack hog

A full printf can need several hundred bytes of stack per call. That is one reason the course prints with its own small uart_puts / uart_put_dec functions.
