Module 20 · AUTOSAR Classic

Writing MCAL Drivers the AUTOSAR Way

The MCAL is where AUTOSAR meets the registers you have been programming since module 05. The register work does not change; what changes is everything around it: standard names and types, configuration kept out of the code, memory sections, and a defined way to report misuse. This module applies those conventions to Port, Dio, Pwm, Adc, Wdg and Can on the STM32G474, using the course's own drivers in autosar/mcal.

🎭
Analogy

The MCAL is a universal power adapter: the plug on top is the same everywhere (Dio_WriteChannel), the pins underneath fit one country's socket (GPIOB->BSRR). Software above the adapter never learns which country it is in.

20.2Std_Types and Platform_Types

BSW interfaces use the AUTOSAR types, not <stdint.h>: uint8 … uint32, sint16, boolean with TRUE/FALSE, and Std_ReturnType with E_OK/E_NOT_OK (AUTOSAR_CP_SWS_PlatformTypes, AUTOSAR_CP_SWS_StandardTypes). Platform_Types.h is written once per CPU and compiler, so the rest of the stack never depends on what int is.

Error handling then has one vocabulary: a function that can fail returns Std_ReturnType; modules may add their own codes from 0x02 upwards (Can's CAN_BUSY). Compare a home-made convention with the standard one:

20.3API naming: <Ma>_<Api>

Every public symbol carries the module abbreviation from the BSW module list (AUTOSAR_CP_TR_BSWModuleList): functions <Ma>_<Api> (Dio_WriteChannel, Can_Write), macros and error codes <MA>_… (DIO_E_PARAM_INVALID_CHANNEL_ID), types <Ma>_…Type (Dio_ChannelType). Configured objects get symbolic names with the <Ma>Conf_ prefix, generated into <Ma>_Cfg.h:

Each module header also publishes who made it and for which release: DIO_VENDOR_ID, DIO_MODULE_ID, DIO_AR_RELEASE_MAJOR_VERSION and so on. Every .c file checks at compile time that the headers it includes belong to the same release. tools/check-autosar.py checks naming and version macros in CI.

20.5MemMap and compiler abstraction

Two conventions let the same source compile for very different compilers and memories. Compiler abstraction wraps declarations in macros that carry memory classes (AUTOSAR_CP_SWS_CompilerAbstraction). On a Cortex-M every class is empty, so the macros expand to plain C:

20.6Development errors with DET

Calling an API with an invalid channel, a NULL pointer or before Init is a programming error. During development such errors go to the Default Error Tracer: Det_ReportError(ModuleId, InstanceId, ApiId, ErrorId) (AUTOSAR_CP_SWS_DefaultErrorTracer). The checks are compiled only when <MA>_DEV_ERROR_DETECT is STD_ON, so production code pays nothing for them.

⚠️
DET is not DEM

DET is for bugs that tests must find before release; it is usually off in production. Faults of the running system (a lamp that fails, a crystal that does not start, a bus that goes silent) are production errors: they go to the Diagnostic Event Manager and become DTCs a workshop can read (module 22).

20.7Port and Dio on the G4

Port configures every pin once at start-up from its configuration table; Dio reads and writes the pins. Dio has no init function and must be safe to call from any context. On the G4, GPIOx_BSRR sets or clears pins atomically, so Dio needs no critical section:

Channel IDs are 16 × port + pin, so DioConf_DioChannel_StalkLeft = 28 is PB12. The mapping lives in the driver, not in the application.

20.9Can and Wdg on the G4

The Can driver moves frames between the FDCAN1 message RAM (TX FIFO/queue, RX FIFO 0) and CanIf. It is called with hardware object handles (HTH for transmit, HRH for receive) and reports back through callbacks (AUTOSAR_CP_SWS_CANDriver).
