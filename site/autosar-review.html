Module 23 · AUTOSAR Classic

Code That Passes an OEM / Tier-1 Review

Code for a vehicle is read by more people than wrote it: the OEM's reviewers, the supplier's quality team, a safety assessor, and the engineer who maintains it in ten years. This module collects what they check, shows the common findings side by side with the fix, explains traceability from requirement to test, and places ISO 26262 on the map.

23.1The review checklist

🔎
Verification status

Every API, type and rule on this page names its AUTOSAR R25-11 document. The requirement IDs and exact values are still being checked against the R25-11 PDFs; until then they come from the R4.x-era specifications, and no requirement ID is quoted, because the course never makes one up. Progress is tracked in the self-review log.

A review checklist turns "is this good code?" into questions with yes/no answers. This one combines the AUTOSAR conventions of modules 18–22 with the embedded rules of the whole course. Tick through it for the capstone's stage 3; it remembers your progress in this browser:

Analogy

A review checklist is a pilot's pre-flight checklist: experienced pilots use it precisely because experience makes you skip steps. It does not make the flight safe by itself; it makes forgetting the obvious unlikely.

⚠️
"It works" is not a review argument

Every "before" example in the course works on the bench. Reviews exist for the cases a bench test never hits: the crystal that fails in winter, the interrupt that lands between two instructions, the next engineer who moves the function to another ECU.

23.3Requirements traceability

Traceability links each requirement to the design and code that implement it and to the tests that verify it, in both directions. 23.4A word on ISO 26262

ISO 26262 is the functional safety standard for road vehicles. It does not tell you how to write a driver; it tells you how much rigour each function needs, based on how bad its failure could be:

LevelMeaningTypical example (depends on the analysis)
QMquality management is enoughinfotainment, comfort functions
ASIL Alowest safety integrity levelsome lighting functions
ASIL Binstrument cluster warnings, some body functions
ASIL Csome powertrain functions
ASIL Dhigheststeering, braking

The ASIL comes from a hazard analysis that rates severity, exposure and controllability of each failure. It then sets requirements across the whole lifecycle: methods for requirements, design, coding (MISRA C, defensive programming), verification (coverage targets), and the hardware itself.

  • Freedom from interference: software of a lower ASIL must not corrupt software of a higher one, in memory, timing or communication. AUTOSAR's OS-Applications with memory protection, timing protection and E2E-protected messages exist for this.
  • Hardware matters: ASIL C/D microcontrollers have lockstep cores, ECC on RAM and flash, and self-tests. The STM32F103 has none of these, which is one reason it is not an automotive part (appendix C).
ℹ️
This course is QM

Nothing in this course is developed to ISO 26262, and the TurnLight capstone is not a safety-qualified turn-signal function. The point here is to know where the standard applies and what it asks for.
