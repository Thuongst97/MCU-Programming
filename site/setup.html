Setting Up and Running a Program on the NUCLEO-G474RE

By the end of this module the NUCLEO-G474RE on your desk blinks its green LED, switches itself from 16 MHz to 170 MHz, prints Hello from NUCLEO-G474RE @ 170 MHz on your PC, and stops at a breakpoint in your debugger. One USB cable does all of it: the board's built-in ST-LINK powers the chip, programs it, debugs it and carries its serial output.

ℹ️
Have an STM32G474VET6 instead?

The VET6 is the same chip in a 100-pin package. Firmware, registers and alternate-function numbers are identical; only the physical pin numbers differ, and your board will not have the NUCLEO's ST-LINK, LD2 or B1 unless its designer added them. The pinout shows both package numbers for every pin. Connect an external ST-LINK to SWDIO/SWCLK/GND/NRST and use the same OpenOCD configuration.

2.2The board: ST-LINK, LD2, B1 and jumpers

A NUCLEO board is two boards on one PCB. The top part is an ST-LINK/V3E debug probe with its own USB connector; the bottom part carries the STM32G474RET6, two buttons, a user LED and two sets of headers (UM2505). The probe talks to the target over SWD (Serial Wire Debug: SWDIO on PA13, SWCLK on PA14) and bridges the target's LPUART1 (PA2 TX, PA3 RX) to a virtual COM port on your PC.

PartPinWhat the course does with it
LD2, green user LEDPA5 (Arduino D13)Blinks. Active-high: driving PA5 to 1 lights it.
B1, blue USER buttonPC13Input in modules 05, 06 and 13. ST's board support reads it as 1 when pressed; check yours.
B2, black RESET buttonNRSTRestarts the program.
Virtual COM portPA2 / PA3 (LPUART1)Every uart_puts() in the course ends up here.
SWDPA13 / PA14Flashing and debugging. Never reconfigure these two pins.

At reset the chip decides where to start from the PB8-BOOT0 pin and option bits. On a NUCLEO as delivered it runs your program from main flash at 0x08000000 (RM0440, boot configuration). Module 03 explains the other modes, and why anything that pulls PB8 high at reset is a problem.

💡
No wiring, no TX/RX swaps

On boards with a separate probe and USB-UART adapter, half of the first-day problems are swapped wires and a missing ground. The NUCLEO routes SWD, NRST and the UART on the PCB, so if something does not work, the cause is in software or in the USB connection.

2.3Install the environment

You need five things: a cross-compiler that produces Arm Cortex-M code (arm-none-eabi-gcc), CMake and Ninja to drive it, OpenOCD to talk to the ST-LINK, and VS Code with the Cortex-Debug extension as a debugger front end. The table shows the versions CI uses; newer ones usually work.

  1. CMake and Ninja from a terminal (PowerShell):
  2. Arm GNU Toolchain: download the arm-none-eabi Windows installer from Arm's download page and tick Add path to environment variable on the last screen. The xPack build (xpack-arm-none-eabi-gcc) is an equivalent zip if you prefer no installer.
  3. OpenOCD: unzip the xPack OpenOCD release for Windows and add its bin folder to PATH.
  4. ST-LINK USB driver: install ST's STSW-LINK009 driver package, then plug the NUCLEO in. Device Manager should list the ST-LINK under "Universal Serial Bus devices" and a "STMicroelectronics STLink Virtual COM Port" under "Ports (COM & LPT)".
  5. VS Code and its extensions: Cortex-Debug (marus25), CMake Tools and C/C++. Opening this repository suggests them automatically (.vscode/extensions.json).
  6. Serial terminal: PuTTY, or the Serial Monitor extension in VS Code.

On Ubuntu or Debian, the distribution packages cover everything except the Arm compiler. The repository's installer downloads exactly the version CI uses into a folder you choose and prints its bin directory:

The openocd package installs udev rules that let a logged-in user open the ST-LINK. Unplug and replug the board after installing. If OpenOCD reports LIBUSB_ERROR_ACCESS, see Troubleshooting. For the serial port, add yourself to the dialout group and log in again.

Then install VS Code with the Cortex-Debug, CMake Tools and C/C++ extensions.

No USB driver is needed for the ST-LINK on macOS. In VS Code install Cortex-Debug, CMake Tools and C/C++.

🎭
Analogy

A cross-compiler is like a translator who lives in your office but writes letters in a language spoken in another country: it runs on your x86 or Apple laptop and writes Thumb-2 machine code for the Cortex-M4. The ST-LINK is the courier that carries the letter to the chip and can knock on its door at any time to ask what it is doing.

💡
Update the ST-LINK firmware once

Older ST-LINK firmware can confuse newer OpenOCD and CubeProgrammer releases. STM32CubeProgrammer has a Firmware upgrade button for the probe; do it once before you start.

ℹ️
Why registers?

The HAL is fine for products, but it hides the hardware you need to understand when something goes wrong, and an automotive ECU does not use it: its drivers come from an AUTOSAR MCAL. HAL appears only on this page. Appendix D shows ST's thinner LL drivers for comparison.

2.6Path A: STM32CubeIDE + HAL

Install STM32CubeIDE (ST account required), then:

  1. File → New → STM32 Project, open the Board Selector tab and pick NUCLEO-G474RE. Answer No when asked to initialise all peripherals with their default mode, so you see every choice.
  2. In the Pinout & Configuration tab: System Core → SYS → Debug: Serial Wire. Do this first.
  3. Click PA5 and choose GPIO_Output. Under Connectivity → LPUART1 choose Asynchronous, 115200 baud, and check that it uses PA2/PA3.
  4. Clock Configuration tab: PLL source HSI, M = /4, N = ×85, R = /2, system clock mux on PLLCLK. The tool turns any limit you break red and sets boost mode and the wait states for you.
  5. Save: CubeMX generates main.c, stm32g4xx_hal_msp.c and the startup file. Build with the hammer, run with the green arrow.
⚠️
Don't skip "Debug: Serial Wire"

If SYS → Debug stays unset, generated init code may turn PA13/PA14 into ordinary GPIOs. The first flash works, and after that the ST-LINK can no longer connect to a running program. Recovery: connect under reset.

⚠️
The stack lives in RAM, not in CCM SRAM

Our script puts the initial stack pointer at the top of the 96 KB SRAM1+SRAM2 region (0x20018000), not in CCM SRAM: a DMA transfer from a buffer on the stack would otherwise fail silently, because DMA cannot reach CCM SRAM. Module 03 takes the linker script apart line by line.

2.9Blink LD2 on PA5 (active-high)

Blinking an LED takes three steps on any STM32: turn on the clock of the GPIO port, configure the pin as an output, and write to it. On the NUCLEO, LD2 sits between PA5 and ground through a resistor, so the LED lights when PA5 is driven high (UM2505; ST's board support package drives it the same way).

The pin's mode lives in GPIOA_MODER: two bits per pin. Below is the value after led_init(). Change MODE5 and watch the C expression change; look at MODE13/MODE14 too: those are the SWD pins, in alternate-function mode from reset.

⚠️
PA5 has two jobs

PA5 is also Arduino D13 and the SCK pin of SPI1. If you use SPI1 on its default pins, the LED flickers with the SPI clock and the LED's resistor loads the clock line. The course uses SPI2 for the flash chip in module 11 for this reason.

2.10From HSI16 to the PLL at 170 MHz

After reset the chip runs from HSI16, an internal 16 MHz RC oscillator: available instantly, accurate to about 1 % (DS12288 gives the exact spread over temperature). The PLL divides it by 4 (PLLM), multiplies by 85 (PLLN, giving a 340 MHz VCO) and divides by 2 (PLLR) to reach the 170 MHz maximum. The board's 24 MHz crystal (HSE) is not needed for that. ⚠️
Three things that 170 MHz needs

Boost mode: above 150 MHz the core regulator must run in range 1 boost (PWR_CR5.R1MODE = 0). Four flash wait states before the clock goes up: FLASH_ACR_LATENCY_4WS, which on the G4 is a real value macro (it equals 4). A ÷ 2 step: when SYSCLK jumps above 80 MHz, the AHB prescaler must be ÷ 2 for at least 1 µs before it goes to ÷ 1, so the supply current rises gently (RM0440, RCC). Skip any of them and the program crashes in ways that look random.

🎭
Analogy

Switching clocks is like speeding up a factory conveyor. You first switch the power plant to its high-output mode (boost), tell the slow station (flash) to take four extra beats per item, start the fast motor (PLL) and wait until it runs smoothly, move the belt onto it at half speed, and only then open the throttle. Doing it in any other order drops parts on the floor.

On hardware the difference is visible: the same crude_delay(400000) loop blinks about ten times faster after the switch, because the loop now runs at 170 million instead of 16 million cycles per second.

2.11"Hello from NUCLEO-G474RE" over LPUART1

The ST-LINK's virtual COM port is wired to LPUART1 on PA2 (TX) and PA3 (RX). LPUART1 sits on APB1, which runs at the full 170 MHz here. PA2 and PA3 must be handed to the peripheral: alternate-function mode, alternate function number 12 (DS12288).

And main() ties it together: slow blinks, the switch, fast blinks, then SysTick for proper timing.

Open a terminal on the ST-LINK's virtual COM port at 115200 baud, 8 data bits, no parity, 1 stop bit (8N1), press the black reset button B2, and you should see exactly this (from expected-output.txt):

Find "STMicroelectronics STLink Virtual COM Port (COMn)" in Device Manager under "Ports (COM & LPT)", then in PuTTY choose Serial, that COM port and speed 115200.

💡
Garbage characters?

Wrong baud rate on one side. If you see garbage only after the clock switch, the code computed BRR for the wrong clock. Troubleshooting lists the checks.

2.13Debug: breakpoints, stepping, SVD

The repository ships a ready VS Code configuration. Open the repository folder, press F5, and Cortex-Debug builds the example, starts OpenOCD, flashes the ELF and stops at the first line of main().

The svdFile entry gives the debugger a description of every peripheral register, so the XPERIPHERALS panel shows RCC, GPIOA and the others field by field. ST's SVD file is not stored in this repository (its licence is unclear); one command downloads it and checks its hash:

Things to try in your first session:

  1. Set a breakpoint on RCC->CFGR = (RCC->CFGR & ~RCC_CFGR_SW) | RCC_CFGR_SW_PLL; in clock_170mhz(). Open XPERIPHERALS → RCC → CFGR, step over the line (F10) and watch SWS change to PLL.
  2. Add s_ms to Watch, continue (F5) and pause: it holds the milliseconds since SysTick started.
  3. In the Debug Console, type -exec info registers to see the core registers, or -exec x/4wx 0x08000000 to see the first four words of the vector table: the initial stack pointer 0x20018000 comes first.
ℹ️
Where printf goes

This course prints over a real UART that the ST-LINK forwards to your PC. Semihosting (sending text through the debug probe) is very slow and stops the program when no debugger is attached; SWO tracing on PB3 is an option with the ST-LINK/V3. Module 15 compares them.

2.14Working without the board

Some MCU courses let you run every example in a simulator. That is not possible here: the open-source simulator Renode has no model of the STM32G4, and a simulator that only approximates the clock tree, the ADC or FDCAN would teach the wrong lessons anyway. Every example in this course is written for, and checked against, the real NUCLEO-G474RE.
