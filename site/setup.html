Setting Up and Running a Program on STM32F103C8T6 Blue Pill

By the end of this module a Blue Pill on your desk blinks its LED, switches itself from 8 MHz to 72 MHz, prints Hello from Blue Pill @ 72 MHz on your PC, and stops at a breakpoint in your debugger. You will also run the very same binary in the Renode simulator, with no hardware at all.

ℹ️
64 KB, not 128 KB

The C8 part is specified with 64 KB of flash. Many chips answer 128 KB when a tool asks, and the upper half often works, but nothing guarantees it. This course never uses it: our linker script and OpenOCD configuration both say 64 KB. Board quirks explains why.

2.2Wiring SWD and BOOT jumpers

SWD (Serial Wire Debug) needs only two signals plus ground: SWDIO (data, PA13) and SWCLK (clock, PA14). On most Blue Pills they come out on the 4-pin header at the end opposite the USB connector. The ST-Link can also power the board through its 3.3 V pin while you flash.

FromToSignal
ST-Link SWDIOBlue Pill SWD header DIO (PA13)Debug data, bidirectional
ST-Link SWCLKBlue Pill SWD header CLK (PA14)Debug clock, driven by the probe
ST-Link GNDBlue Pill SWD header GNDCommon ground
ST-Link 3.3VBlue Pill SWD header 3.3Power for the board (only if no other supply)
USB-UART RXPA9USART1 TX → your PC
USB-UART TXPA10Your PC → USART1 RX
USB-UART GNDGCommon ground (always connect it)

Leave both BOOT jumpers on 0. At reset the chip samples the BOOT0 pin (and BOOT1 on PB2) to decide where to start: with BOOT0 = 0 it runs your program from main flash at 0x08000000 (RM0008 §3.4). BOOT0 = 1 starts ST's built-in serial bootloader instead; flashing shows when that is useful.

⚠️
One power source at a time

Power the board from the ST-Link's 3.3 V pin or from its own USB connector, not both. On most boards the regulator output is tied straight to the 3.3 V header pin, so two supplies end up fighting each other. If the USB cable is plugged in, leave the ST-Link 3.3 V wire off and keep GND connected.

💡
TX goes to RX

A UART line has one talker and one listener, so the board's TX (PA9) goes to the adapter's RX, and the adapter's TX goes to PA10. PA9 and PA10 are 5 V tolerant (DS5319 Table 5), but a 3.3 V adapter stays safe even if you later move a wire to a pin that is not.

Why registers?

The HAL is fine for products, but it hides the hardware you need to understand when something goes wrong, and an automotive ECU does not use it: its drivers come from an AUTOSAR MCAL. HAL appears only on this page. Appendix D shows ST's thinner LL drivers for comparison.

2.6Path A: STM32CubeIDE + HAL

Install STM32CubeIDE (ST account required), then:

  1. File → New → STM32 Project, pick STM32F103C8Tx.
  2. In the Pinout & Configuration tab: System Core → SYS → Debug: Serial Wire. Do this first.
  3. System Core → RCC → High Speed Clock: Crystal/Ceramic Resonator.
  4. Click PC13 and choose GPIO_Output. Under Connectivity → USART1 choose Asynchronous, 115200 baud.
  5. Clock Configuration tab: input 8 MHz, PLL source HSE, multiplier ×9, APB1 prescaler /2. The tool turns any limit you break red.
  6. Save: CubeMX generates main.c, stm32f1xx_hal_msp.c and the startup file. Build with the hammer, run with the green arrow.
⚠️
Don't skip "Debug: Serial Wire"

If SYS → Debug stays at No Debug, the generated init code releases PA13/PA14 from the debug port. The first flash works, and after that the ST-Link can no longer connect to a running program. Recovery: connect under reset or boot with BOOT0 = 1.

2.9Blink PC13 (active-low)

Blinking an LED takes three steps on any STM32F1: turn on the clock of the GPIO port, configure the pin as an output, and write to it. The on-board LED sits between 3.3 V and PC13, so current flows, and the LED lights, when PC13 is driven low.

The pin configuration lives in GPIOC_CRH: four bits per pin (MODE and CNF) for pins 8 to 15. Below is the value after led_init(). Change MODE13 or CNF13 and watch the C expression change; then try another port.

⚠️
PC13 is a weak pin

PC13, PC14 and PC15 can sink only about 3 mA, must run at 2 MHz or less, and must not source current (DS5319, Table 5 notes). That is enough for the on-board LED and nothing more. Never hang a relay or a bright LED on them; that is why led_init() picks the 2 MHz output mode.

2.10From HSI 8 MHz to PLL 72 MHz

After reset the chip runs from HSI, an internal 8 MHz RC oscillator: available instantly, but only accurate to about 1 % at room temperature and worse across the temperature range (DS5319). The Blue Pill also carries an 8 MHz crystal (HSE). The PLL multiplies it by 9 to reach the 72 MHz maximum. The order of the steps matters:

This is RCC_CFGR after a successful switch. SWS (read-only) now reports the PLL, which is how the code knows the switch really happened:

⚠️
FLASH_ACR_LATENCY_2 is not "two wait states"

In the CMSIS header, FLASH_ACR_LATENCY_2 is the mask of bit 2 of the field, value 0x4. Writing it asks for four wait states, which the F1 does not define. Two wait states is the value 2 in the field: (2U << FLASH_ACR_LATENCY_Pos). Too few wait states at 72 MHz makes the CPU read flash before the data is ready, and the program crashes in ways that look random.

🎭
Analogy

Switching clocks is like changing the conveyor speed in a factory. You first tell the slow station (flash) to take two extra beats per item, then start the fast motor (PLL) and wait until it runs smoothly, and only then move the belt onto it. Doing it in any other order drops parts on the floor.

On hardware the difference is visible: the same crude_delay(200000) loop blinks nine times faster after the switch, because the loop now runs at 72 million instead of 8 million cycles per second.

2.11"Hello from Blue Pill" over USART1

USART1 sits on the APB2 bus, which runs at the full 72 MHz here. Its transmit pin is PA9, so PA9 must be handed to the peripheral (an alternate function output) instead of being a plain GPIO.

And main() ties it together: slow blinks, the switch, fast blinks, then SysTick for proper timing.

Open a terminal at 115200 baud, 8 data bits, no parity, 1 stop bit (8N1), press the Blue Pill's reset button, and you should see exactly this (from expected-output.txt):

Find the adapter's port in Device Manager under "Ports (COM & LPT)", then in PuTTY choose Serial, that COM port and speed 115200.

💡
Garbage characters?

Wrong baud rate on one side. If you see garbage only after the clock switch, the code computed BRR for the wrong clock. Troubleshooting lists the checks.

2.13Debug: breakpoints, stepping, SVD

The repository ships a ready VS Code configuration. Open the repository folder, press F5, and Cortex-Debug builds the example, starts OpenOCD, flashes the ELF and stops at the first line of main().

The svdFile entry gives the debugger a description of every peripheral register, so the XPERIPHERALS panel shows RCC, GPIOC and the others field by field. ST's SVD file is not stored in this repository (its licence is unclear); one command downloads it and checks its hash:

Things to try in your first session:

  1. Set a breakpoint on RCC->CFGR = (RCC->CFGR & ~RCC_CFGR_SW) | RCC_CFGR_SW_PLL; in clock_72mhz(). Open XPERIPHERALS → RCC → CFGR, step over the line (F10) and watch SWS change to PLL.
  2. Add s_ms to Watch, continue (F5) and pause: it holds the milliseconds since SysTick started.
  3. In the Debug Console, type -exec info registers to see the core registers, or -exec x/4wx 0x08000000 to see the first four words of the vector table: the initial stack pointer 0x20005000 comes first.
ℹ️
Where printf goes

This course prints over a real UART. Semihosting (sending text through the debug probe) is very slow and stops the program when no debugger is attached, and SWO tracing needs the probe's SWO pin, which most ST-Link V2 clones lack. Module 15 compares the options.

2.14Run without hardware in Renode

Renode is an open-source simulator from Antmicro. It runs the same ELF you would flash, on a model of the STM32F103, and shows the UART output in a window. The course's model (examples/common/renode/bluepill.repl) adds what Renode's stock STM32F103 platform lacks for our examples: a clock controller that reports the PLL as locked and switched, a flash interface, and the bit-band regions the HAL uses.
