Capstone 2: The Same ECU on FreeRTOS

Stage 2 rebuilds the TurnLight ECU on FreeRTOS. The state machine, the lamp monitor, the message packing and the board layer are the same files as in stage 1; only the integration changes. The question this module answers is what you gain and what you pay for it.

⏱ 40 min read🎯 Advanced📂 capstone/turnlight/stage2-freertos

25.1Task design

Tasks are chosen by deadline and by what they wait for, not by source file:

TaskPriorityRunsWaits on
lamp4 (highest)every 5 msvTaskDelayUntil: the ramp must be smooth
input3every 10 msvTaskDelayUntil; sends edges to a queue
logic3every 10 msvTaskDelayUntil; lamp monitor + state machine
can2on change, else every 10 msan event group bit with a 10 ms timeout
supervisor1 (lowest)every ~50 msall four check-in bits

The supervisor has the lowest priority on purpose: if any higher task runs away and starves the CPU, the supervisor never gets to feed the watchdog, and the ECU resets. A watchdog fed from a high-priority task would keep a broken ECU alive.

🎭
Analogy

Stage 1 is one cook who does every job in turn; if one dish takes too long, every other dish waits. Stage 2 is a brigade: each cook has one station, and the head chef (the scheduler) always lets the most urgent order through first.

25.2Queues and events

Tasks share nothing by accident. Three FreeRTOS objects carry all the data:

  • a queue of button edges, input → logic: no edge is lost even if the logic task is late;
  • a one-element mailbox (xQueueOverwrite / xQueuePeek) holding the latest outputs, logic → lamp and can: readers always get the newest complete snapshot, never a half-updated one;
  • event groups: one bit "status changed" logic → can, and one bit per task for the supervisor.
⚠️
The UART is shared too

Four tasks print to one UART. Without the mutex in log3(), a higher-priority task could interrupt a line halfway and mix two log messages, and anyone reading the log, a person at a terminal or a script, would see garbled lines at random. Any resource used by more than one task needs a lock or a single owner.

25.4What changed

The same requirement, two integrations: the supervisor.

AspectStage 1: bare metalStage 2: FreeRTOS
Flash / RAM (debug build)about 9.8 KB / 2.6 KBabout 23 KB / 9.6 KB (kernel + 5 stacks)
A slow jobdelays every other jobonly delays lower-priority tasks
Waiting in the middle of a jobimpossible; split into statesnatural: block on a queue or event
Shared dataplain globals, one contextqueues, mailbox, mutex
New failure modesoverrunspriority inversion, stack overflow, deadlock
Acceptance suiteidentical, and passes for both

For an ECU this small, bare metal is a perfectly good answer. The RTOS pays off when jobs start to wait for things (a flash write, a diagnostic session, a bus) and when more people add features.
