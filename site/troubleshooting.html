Troubleshooting

Start from what you see. Each entry lists the likely causes in the order worth checking, and the fix. Most problems are wiring, a pin the board already uses, or a setting in the debugger configuration.

⏱ Reference🎯 All levels🔎 Symptom first

B.1ST-LINK not detected

You see: Error: open failed, LIBUSB_ERROR_ACCESS, or No ST-Link detected.

  1. Is the ST-LINK on the bus at all? Linux: lsusb should list a 0483:37xx device from STMicroelectronics (an STLINK-V3). Windows: Device Manager should show it under Universal Serial Bus devices, plus a COM port for the virtual COM port. If not, try another cable or port: charge-only cables are common. The ST-LINK's communication LED should light when the board is plugged in.
  2. Linux permissions. The openocd package installs udev rules that give the logged-in user access. Reload them and replug the board:
  3. Windows driver. Install ST's ST-LINK driver package (STSW-LINK009, which covers the V3) and replug. If another tool replaced the driver, reinstall ST's.
  4. Another program holds the probe. Only one tool can own the ST-LINK: close STM32CubeIDE, CubeProgrammer or a running OpenOCD. (A serial terminal on the virtual COM port is fine.)

B.2Old ST-LINK firmware or wrong OpenOCD target

You see: OpenOCD finds the ST-LINK but warns that its firmware is old, or fails with an unknown device or flash bank error.

  • Firmware. OpenOCD and IDEs expect a recent ST-LINK firmware. Update it with STM32CubeProgrammer (Firmware upgrade) or ST's stand-alone ST-LINK upgrade tool, then replug.
  • Target script. The G474 needs target/stm32g4x.cfg; an STM32F1 or L4 script talks to the wrong flash controller. Use the course's configuration, which loads the right one:
⚠️
Don't edit OpenOCD's installed scripts

Editing target/stm32g4x.cfg fixes it on your machine only and is undone by the next update. Keep any difference in the project: nucleo-g474re.cfg, and the matching entry in .vscode/launch.json.

B.3Cannot halt target / SWD locked out

You see: the first flash worked, but now Error: init mode failed (unable to connect to the target) or timed out while waiting for target halted.

The probe can only talk to the chip while PA13/PA14 are in their debug alternate function (AF0) and the core is awake. Your program probably took that away right after reset: it changed MODER13/MODER14 or AFRH of GPIOA, entered Stop/Standby/Shutdown immediately, or crashed into a loop with the clocks misconfigured.

Fix 1: connect under reset

On the NUCLEO, the ST-LINK drives NRST, so OpenOCD can hold the chip in reset while it connects, before your program runs:

Then erase or reflash a fixed program. STM32CubeProgrammer offers the same as "Mode: Under reset".

Fix 2: boot into the system bootloader

  1. Pull PB8 (BOOT0, Arduino D15) to 3.3 V with a jumper wire and press B2 (RESET). With the factory option bits (nSWBOOT0 = 1, nBOOT1 = 1) the chip now runs ST's ROM bootloader instead of your program, so SWD stays free.
  2. Connect and erase everything: (the G4 uses OpenOCD's stm32l4x flash driver)
  3. Remove the wire, fix the program, flash again.
⚠️
RDP level 2 cannot be undone

If the option bytes were set to read-out protection level 2, the debug port is closed for good and neither fix works. That is why the course never sets it (module 16).

B.4The board starts ST's bootloader

You see: after a reset or power-up your program does not run (no LD2, no output), but the debugger connects and the PC is somewhere around 0x1FFF0000.

  • Something pulls PB8 high at reset. PB8 (Arduino D15) is BOOT0 while nSWBOOT0 = 1. An I2C module with pull-ups on D14/D15, a shield, or a wire left from Fix 2 above is enough. Move the signal (example 06 uses I2C2 on PA9/PA8 for exactly this reason) or remove the wire.
  • Option bits. Check nSWBOOT0, nBOOT0 and nBOOT1 in FLASH_OPTR (board reference). Setting nSWBOOT0 = 0 and nBOOT0 = 1 makes the chip ignore PB8 and always boot from flash.
  • Empty flash. A chip that was mass-erased has nothing to run; flash a program.

B.5LD2 does not light

You see: the program runs (the UART prints), but LD2 stays dark, glows dimly, or does the opposite of what you expect.

  • Port clock off: GPIOA needs RCC_AHB2ENR.GPIOAEN before any GPIOA register write takes effect.
  • Still analog: after reset PA5 is in analog mode (MODE5 = 11). It must be 01 (output):
  • Inverted: LD2 is active-high: GPIO_BSRR_BS5 turns it on. If yours behaves the other way round, you are probably looking at a different board's code (a Blue Pill's PC13 LED is active-low).
  • Flickers or stays off with SPI running: PA5 is also SPI1_SCK. The course uses SPI2 on PB13–PB15 to keep PA5 for the LED.

B.6Garbage on the UART

You see: random characters, or text only before or after a certain point.

  1. Baud rate: the terminal and the firmware must both use 115200 8N1, with no flow control.
  2. LPUART is not USART: the virtual COM port is LPUART1, whose BRR is 256 × fck / baud, not fck / baud. Using the USART formula gives a rate 256 times off: nothing readable at all (module 08).
  3. The clock the firmware assumed: BRR is computed from LPUART1's kernel clock. If the code assumes 170 MHz but the PLL switch failed (the chip still runs at 16 MHz on HSI16), every bit is more than ten times too long. Print the clock status, as example 00 does, and check RCC_CCIPR.LPUART1SEL.
  4. Wrong pins: the ST-LINK listens on PA2/PA3 with AF12. D0/D1 on the Arduino header are PC5/PC4, not the virtual COM port.
💡
Measure, don't guess

Send U (0x55) in a loop: on a logic analyser on PA2 it is a clean square wave whose bit time tells you the real baud rate.

B.7Hangs during clock setup

You see: the program never gets past clock setup, reports a non-zero clock status, or crashes right after switching to 170 MHz.

  • Not enough wait states: raise FLASH_ACR.LATENCY to 4 (FLASH_ACR_LATENCY_4WS) before switching to 170 MHz. Too few wait states read wrong instructions from flash: random HardFaults.
  • Boost mode off: above 150 MHz, range 1 boost (PWR_CR5.R1MODE = 0) is required.
  • No AHB ÷2 step: switching SYSCLK above 80 MHz needs the AHB prescaler at ÷2 for at least 1 µs, then ÷1 (module 04).
  • PLL never locks: the VCO input and output must stay within their limits (HSI16 / M between 2.66 and 16 MHz, VCO between 64 and 344 MHz), and RCC_PLLCFGR may only change while the PLL is off. The course's code gives up after a timeout and stays on HSI16. Route SYSCLK to PA8 with MCO to check it with a scope.

B.8Flash programming errors

You see: your own flash code (a bootloader, a data logger) fails with an error flag in FLASH_SR, or OpenOCD reports a flash write error.

  • PGSERR, PGAERR, SIZERR: the G4 programs 64-bit double words, 8-byte aligned, low word first. A lone 32-bit write or a misaligned address sets one of these.
  • PROGERR: the double word was not erased. Each double word can be programmed once per erase (it carries ECC).
  • WRPERR: the page is write-protected by the option bytes.
  • Stale flags: error flags stay set until written with 1. Clear them before starting an operation, as example 12's wait_done() does.
  • Wrong page number: the page size is 2 KB with DBANK = 1 (factory default) and 4 KB with DBANK = 0; in dual-bank mode, bank 2 also needs BKER (module 16).

B.9CAN sends nothing

You see: nothing on the bus, transmit requests never complete, or the error counters climb.

  1. No other node: every CAN frame must be acknowledged by at least one other node. Alone on a bus, the controller resends forever and its transmit error counter rises. Test alone with FDCAN's internal loopback mode (CCCR.TEST + TEST.LBCK with CCCR.MON) first.
  2. Stuck in initialization: after CCCR.INIT is cleared, FDCAN waits for 11 recessive bits on FDCAN1_RX before it takes part in bus traffic. A floating or shorted RX pin (no transceiver, wrong pin) keeps it waiting. After bus-off, INIT is set again and software must clear it.
  3. Wrong pins or AF: the course uses PA11 (RX) and PA12 (TX) with AF9. They are on the Morpho header, not the Arduino header.
  4. Physical layer: the NUCLEO has no CAN transceiver. Both boards need one (3.3 V, rated for the CAN FD data rate if you use FD), a twisted pair, a common ground and 120 Ω at each end of the bus.
  5. Bit timing: both nodes must agree on the bit rate and use a similar sample point, in NBTP (and DBTP for the FD data phase). Module 12 has a calculator.
