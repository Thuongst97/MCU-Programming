Module 03 · From reset to main

Startup Code, Vector Table & Linker Scripts

Between pressing reset and the first line of main(), a few hundred instructions run that most programmers never see. This module walks through every one of them, and through the linker script that decides where each byte of your program ends up.

⏱ 40 min read🎯 Beginner → intermediate📂 examples/00-nucleo-blink-uart/bare

3.1Boot modes: PB8-BOOT0 and option bytes

When the chip comes out of reset, it decides which memory to start from and aliases it at address 0x00000000, where the core looks first (RM0440, boot configuration). On the G4 the decision uses one pin and three option bits stored in flash (FLASH_OPTR):

BOOT0nBOOT1 (option bit)Boots fromUse
0xMain flash 0x08000000Normal operation: your program.
11System memory 0x1FFF0000ST's bootloader: load new firmware over USART, I2C, SPI, FDCAN or USB (AN2606), or recover a chip whose program disabled SWD.
10SRAM1 0x20000000Rare: running code a debugger loaded into RAM.

Where BOOT0 itself comes from is another option bit, nSWBOOT0. With the factory setting (nSWBOOT0 = 1) BOOT0 is the level of the PB8-BOOT0 pin, sampled at reset. With nSWBOOT0 = 0 the pin is ignored and BOOT0 is the option bit nBOOT0 instead, which frees PB8 for ordinary use. ST's HAL names the two choices OB_BOOT0_FROM_PIN and OB_BOOT0_FROM_OB.

⚠️
PB8 is also Arduino D15 (I2C1 SCL)

PB8 is a normal I/O pin after reset, and on the NUCLEO it is the Arduino D15 / I2C SCL position. An I2C module with a pull-up resistor on SCL holds PB8 high while the chip resets, so it boots ST's bootloader instead of your program: LD2 stays dark and the debugger finds the PC in system memory. The course therefore puts its I2C OLED on PA9/PA8 (module 10). If you must use PB8 at reset, clear nSWBOOT0 with STM32CubeProgrammer, once, knowingly.

🎭
Analogy

The boot configuration is a railway switch set before the train leaves. Moving the lever while the train is running changes nothing; the next departure takes the new track. The option bits decide whether that lever is the one on the platform (the PB8 pin) or one locked in the signal box (nBOOT0).

3.3The vector table

The vector table is an array of 32-bit words at the start of the image. Word 0 is the initial stack pointer; every word after that is the address of a handler: reset, faults, system exceptions, then the device interrupts in the order of their IRQ numbers. ⚠️
A typo in a handler name fails silently

Write void USART1_IRQHandle(void) (missing "r") and the program still links: your function is simply never called, and the interrupt runs Default_Handler, which loops forever. If your program "hangs" right after enabling an interrupt, halt it in the debugger: a PC inside Default_Handler means a name mismatch.

3.4.text, .data, .bss, stack and heap

The compiler sorts everything it produces into named sections. Five of them matter:

SectionContainsLives inExample
.isr_vectorthe vector tableflash, firstg_vector_table
.text / .rodatacode and constantsflashmain(), const char msg[] = "hi";
.dataglobals with a non-zero initial valueRAM at run time, initial values in flashuint32_t SystemCoreClock = 16000000;
.bssglobals without initial value (or 0)RAM, zeroed by startup; nothing in flashstatic volatile uint32_t s_ms;
stack / heaplocal variables, return addresses; mallocRAM, whatever is left—

The G474 adds a sixth place: the 32 KB CCM SRAM. Our linker script declares it as a region (CCMRAM) but places nothing there, so it stays free for code or data you deliberately move there with a section attribute, never for DMA buffers.

The key idea is the difference between where a section is stored (its load address, LMA) and where it runs (its virtual address, VMA). For .data they differ: the initial values are stored in flash and copied to RAM by the startup code before main().

ℹ️
Why C is safe here

Startup code in C works on Cortex-M because the hardware has already loaded a valid stack pointer before the first instruction. The C code must just avoid using any global variable before the copy loop has run, which ours does.

3.8Pitfalls

⚠️
Floating point before the FPU is on

The build uses -mfloat-abi=hard. If any code that runs before SCB->CPACR enables CP10/CP11 touches an FPU register, even a struct copy the compiler chose to do with vldm/vstm, the core raises a UsageFault with CFSR.NOCP set, and with no fault handler yet, the chip locks up in HardFault. That is why the CPACR write is the very first statement of Reset_Handler.

⚠️
Keep the stack 8-byte aligned and out of CCM SRAM

The Arm procedure call standard asks for an 8-byte aligned stack at every public function call; ORIGIN(RAM) + LENGTH(RAM) = 0x20018000 is. Putting the stack in CCM SRAM looks attractive (it is fast), but a local buffer handed to DMA then never receives a byte, because DMA cannot reach CCM SRAM.

  • Stack overflow is silent. The stack grows down into .bss and .data and corrupts globals. The linker's reserve only checks that space exists at build time. Module 14 shows run-time checks.
  • Forgetting KEEP() on the vector table lets --gc-sections throw it away; the image then starts with code instead of a stack pointer, and the chip never runs.
  • Wrong VTOR after moving the table. A bootloader setup puts the application's vector table at a different address; SCB->VTOR must point to it (module 16).
  • Using globals in startup before they are initialised. Anything that runs before the copy loop sees garbage in .data and .bss.
