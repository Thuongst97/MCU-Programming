Module 03 · From reset to main

Startup Code, Vector Table & Linker Scripts

Between pressing reset and the first line of main(), a few hundred instructions run that most programmers never see. This module walks through every one of them, and through the linker script that decides where each byte of your program ends up.

⏱ 40 min read🎯 Beginner → intermediate📂 examples/00-bluepill-blink-uart/bare

3.1Boot modes: BOOT0 and BOOT1

When the chip comes out of reset, it samples two pins to decide which memory to start from (RM0008 §3.4). The chosen memory is aliased at address 0x00000000, where the core looks first.

BOOT1 (PB2)BOOT0Boots fromUse
x0Main flash 0x08000000Normal operation: your program.
01System memory 0x1FFFF000ST's bootloader: flash new firmware over USART1 (AN2606), or recover a chip whose program disabled SWD.
11Embedded SRAM 0x20000000Rare: running code loaded into RAM by a debugger.

The pins are sampled on the fourth rising edge of the system clock after reset, and again when leaving Standby mode, so changing a jumper takes effect at the next reset, not immediately.

🎭
Analogy

The boot pins are a railway switch set before the train leaves. Moving the lever while the train is running changes nothing; the next departure takes the new track.

3.3The vector table

The vector table is an array of 32-bit words at the start of the image. Word 0 is the initial stack pointer; every word after that is the address of a handler: reset, faults, system exceptions, then the device interrupts in the order of their IRQ numbers. ⚠️
A typo in a handler name fails silently

Write void USART1_IRQHandle(void) (missing "r") and the program still links: your function is simply never called, and the interrupt runs Default_Handler, which loops forever. If your program "hangs" right after enabling an interrupt, halt it in the debugger: a PC inside Default_Handler means a name mismatch.

3.4.text, .data, .bss, stack and heap

The compiler sorts everything it produces into named sections. Five of them matter:

stack / heaplocal variables, return addresses; mallocRAM, whatever is left—

The key idea is the difference between where a section is stored (its load address, LMA) and where it runs (its virtual address, VMA). For .data they differ: the initial values are stored in flash and copied to RAM by the startup code before main().

ℹ️
Why C is safe here

Startup code in C works on Cortex-M because the hardware has already loaded a valid stack pointer before the first instruction. The C code must just avoid using any global variable before the copy loop has run, which ours does.

3.8Pitfalls

⚠️
ST's generic linker script is not for the C8

ST's STM32F103XB_FLASH.ld declares 128 KB of flash (the XB part) and sets _estack = 0x20004FFF, an odd address, one byte below the end of RAM. The Cortex-M3 rounds SP down to a multiple of 4, but the Arm procedure call standard asks for 8-byte alignment at function calls, which matters for 64-bit values and printf. Our script uses ORIGIN(RAM) + LENGTH(RAM) = 0x20005000 and 64 KB.

  • Stack overflow is silent. The stack grows down into .bss and .data and corrupts globals. The linker's reserve only checks that space exists at build time. Module 14 shows run-time checks.
  • Forgetting KEEP() on the vector table lets --gc-sections throw it away; the image then starts with code instead of a stack pointer, and the chip never runs.
  • Wrong VTOR after moving the table. A bootloader setup puts the application's vector table at a different address; SCB->VTOR must point to it (module 16).
  • Using globals in startup before they are initialised. Anything that runs before the copy loop sees garbage in .data and .bss.
