Capstone 3: Refactoring into AUTOSAR Layers

The last stage refactors TurnLight into AUTOSAR layers: two application SWCs with runnables, a hand-written RTE that mirrors generated code, the course's BSW-lite and MCAL, and the OS shim. The black-box behaviour does not change, and the acceptance suite proves it. What changes is where every line lives, and why.

⚠️
The OS underneath is not AUTOSAR

Stage 3 runs on autosar/os_shim, an OSEK-like API over FreeRTOS. Task mapping, alarms and the code structure match an AUTOSAR ECU; timing protection, memory protection and the OS's certification do not exist here (module 21 lists the differences).

26.5Upgrade path: CAN FD

CAN FD (12.9) arbitrates at the classic bit rate, then switches to a faster data phase and carries up to 64 bytes per frame. The F103's bxCAN speaks classic CAN only, so everything in this section is on paper: it is what you would change to move TurnLight to an automotive MCU with a CAN FD controller, such as the families in Appendix C. Nothing here runs on the Blue Pill or in Renode.

TurnLight itself doesn't need it: TurnLightStatus is 4 bytes. CAN FD pays off when frames grow: authenticated messages that carry a MAC and a freshness value, bulk sensor data, and software download over UDS, where 64-byte frames and a faster data phase cut flashing time.

🚚
Same gate, bigger truck

Every vehicle queues at the same toll gate at the same speed: that is arbitration, and it works exactly as in classic CAN. Once through the gate, a CAN FD frame switches to the fast lane and carries a container instead of an envelope. Anyone who only knows envelopes, a classic node, sees something illegal and blocks the road.

Payload, DLC and padding

Above 8 bytes, CAN FD does not allow every length: DLC codes 9 to 15 mean 12, 16, 20, 24, 32, 48 and 64 bytes (ISO 11898-1:2015), so the driver pads up to the next valid size. Move the slider to compare with classic CAN:

What changes, layer by layer

This is the payoff of the layering in 26.1: the change stays below the RTE.

LayerOur file(s)With CAN FD
SWCsTurnLight.c, LampMonitor.cNo change. They read and write signals, never frames.
RTERte.cNo change. It maps ports to Com signals, whatever frame carries them.
ComCom_PBcfg.c, Com.cThe I-PDU length may grow up to 64 bytes in the configuration. Our Com-lite would need more: it keeps 8 bytes per I-PDU (data[8]) and packs signals into bytes 0–3 only.
PduRPduR_PBcfg.cNo change. It routes by PDU ID, not by length or frame format.
CanIfCanIf_PBcfg.cEach TX PDU is configured as a classic or an FD frame, and its length may exceed 8 bytes. The CAN IDs (0x3A0, 0x3A1, hypothetical) stay.
Can driverCan.c, Can_PBcfg.cA new driver for the FD controller. Its configuration holds two bit timings, arbitration phase and data phase, instead of one CAN_BTR value. Our Can_Write rejects any length above 8 today.
HardwareboardAn FD-capable controller, and a transceiver rated for the data-phase rate. The SN65HVD230 is specified for signalling rates up to 1 Mbit/s (SLOS346): fine for classic CAN, not for a 2 or 5 Mbit/s data phase.
⚠️
One classic node breaks an FD bus

A classic CAN controller treats an FD frame as an error and destroys it with an error frame. Every node on the bus must be FD-capable (or FD-tolerant): here that includes the cluster node, which is a second Blue Pill. Migrate the whole network, not one ECU.

26.7Where to go next

Where to go from the Blue Pill:

  • Real tools. Vector DaVinci Configurator and Developer, Elektrobit tresos, ETAS ISOLAR, and the silicon vendors' MCAL configurators generate exactly the files cfg/ and rte/ imitate. Student and evaluation licences exist for some of them.
  • Real automotive microcontrollers. NXP S32K1/S32K3, Infineon AURIX TC3xx and Renesas RH850 come with AUTOSAR MCALs from their vendors and evaluation boards in the price range of a good multimeter. Appendix C maps each course module onto them.
  • Open source. Trampoline is an open OSEK/AUTOSAR OS that can replace the shim; the capstone's API is close enough to port.
  • The specifications. The AUTOSAR documents are free to download; start with the layered architecture and the SWS of a driver you know.
