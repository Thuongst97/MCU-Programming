Module 17 · Embedded engineering

Testing, Static Analysis and MISRA C

Firmware bugs are expensive to find on hardware and very expensive to find in the field. This module moves as much checking as possible to your PC: logic tested on the host with Unity, the compiler and cppcheck reading every line, and MISRA C as a shared list of what tends to go wrong in C. Every technique here runs in the course's CI on every push.

⏱ 45 min read🎯 Intermediate📂 tests/host, examples/common/gallery, tools/run-misra.py

17.1Designing for testability

Code that reads registers directly can only run on the chip. Code that turns inputs into outputs can run anywhere. The trick is to keep the two apart: a thin layer touches the hardware, and everything interesting sits behind it as plain C. The course's examples are built that way: debouncing, the scheduler, the ring buffer, the shell, ADC scaling, the font renderer, the JEDEC decoder, the fault decoder and the bootloader's protocol are all pure functions with host tests.

Three ways to cut the hardware out of a unit under test:

SeamHowCourse example
Pure functionpass values in, get values out; the caller does the I/Odebounce_update(state, raw_level, now), proto_feed(parser, byte)

🎭
Analogy

A flight simulator. Pilots practise engine failures in a simulator because the real thing is too expensive and too rare to train on. A host test is a simulator for your logic: you can feed it the 0xFFFFFFFF tick wrap, the corrupted frame and the full buffer as often as you like.

CMock, only when you need it

When a module calls another module whose behaviour the test must control (a driver that returns errors, a function that must be called exactly twice), CMock generates a mock from the header. Its generator needs Ruby on the author's machine; the generated files are committed so CI does not need Ruby. Hand-written fakes like capture() above are simpler and cover most cases.

⚠️
The host is not the target

Your PC has 64-bit pointers, a different long and maybe a different char signedness. Use the fixed-width types from <stdint.h> everywhere, and never test timing or register behaviour on the host: that is what Renode and the board are for.

17.3Static analysis

Static analysis reads code without running it. Turn on everything cheap first:

  • Compiler warnings: the course builds with -Wall -Wextra -Werror -Wshadow -Wconversion and friends (module 02). Every warning is a build failure, so warnings never pile up.
  • cppcheck: finds undefined behaviour, out-of-bounds indexes, uninitialised variables, and with its MISRA addon checks a large share of the MISRA C rules. Run in CI by tools/run-misra.py.
  • GCC's -fanalyzer and clang-tidy: deeper path-sensitive checks; slower, useful before a release.

The tool works as a ratchet: the findings that existed when the check was introduced are counted per file and rule in tools/misra-baseline.json. CI fails when any count goes up, so new code must be clean while old findings are fixed one by one.

17.4MISRA C in practice

MISRA C is a set of guidelines for C in critical systems, first written for the motor industry and now used across automotive, rail, medical and aerospace. It restricts the language to a subset with fewer surprises: no undefined behaviour, no reliance on implementation-defined behaviour without documenting it, explicit types, simple control flow.

CategoryMeaningExample rule numbers
Mandatoryalways followed; no deviation allowedRule 9.1 (reading a variable before it is set), Rule 17.3 (implicitly declared functions)
Requiredfollowed, or a formal deviation is recordedRule 10.4 (mixing essential types in one operation), Rule 21.3 (dynamic memory)
Advisorygood practice; may be disapplied for a project, with a recordRule 15.5 (where a function returns), Rule 12.1 (implicit operator precedence)

Two kinds of guideline: rules, which a tool can check from the code, and directives, which need documents or reviews (for example, that run-time failures are minimised by design). The course uses MISRA C:2012 numbering including its amendments, because that is what industry projects and the cppcheck addon use. The guideline texts are copyrighted: the course names rule numbers and explains their intent in its own words. Buy the document from MISRA if you work to it.

📘
About the newer edition

MISRA has since published a consolidated edition of MISRA C that folds the 2012 amendments into one document. Its rule numbers largely follow the 2012 scheme. Projects usually stay on the edition in their contract; check which one yours names before citing rule numbers.

🎭
Analogy

MISRA is a traffic code. Most of its rules exist because someone crashed: "no overtaking on a hill" looks arbitrary until you meet a truck. The deviation process is the police escort: you may break a rule, but only with a recorded reason and someone who signed off.

⚠️
The bugs that pass casual tests

Every "before" version works for the obvious inputs: positive temperatures, small buffers, the first 49 days of uptime. They fail on the edge, in the field. Write tests for the edges on purpose: zero, the maximum, negative values, the wrap-around.

17.6Writing a deviation record

Sometimes a rule cannot be followed. Accessing a peripheral register means converting an integer address into a pointer, which a required rule restricts; the CMSIS headers do exactly that in every GPIOA->ODR. MISRA's answer is not "ignore it" but a deviation: a written record that says which rule, where, why it cannot be followed, and why the result is still safe, approved by someone other than the author.

The course's own stance (docs/misra/compliance.md): mandatory and required rules are never disapplied, advisory Rule 15.5 is disapplied for the whole project with a recorded reason (early returns in guard clauses), and any single exception is marked in the code with an inline suppression naming its record, such as // cppcheck-suppress misra-c2012-11.5 ; DEV-002.

💡
A good deviation is rare and boring

If you write the same deviation five times, change the design instead (wrap the construct in one function with one deviation). Reviewers trust a project with three precise deviations more than one with three hundred vague ones.
