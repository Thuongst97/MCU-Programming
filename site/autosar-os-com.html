OS, Scheduling and the COM Stack

Runnables need something to run them, and signals need a way onto the bus. This module covers the AUTOSAR OS (and the course's honest stand-in for it), how runnables and BSW main functions are mapped to tasks, and the communication stack: one signal's journey from an SWC through Com, PduR, CanIf and the Can driver to a frame on the wire.

The AUTOSAR OS (AUTOSAR_CP_SWS_OS) is based on OSEK/VDX OS (ISO 17356-3): everything is configured statically, nothing is created at run time. Its objects:

⚠️
Order inside a task is a design decision

Can_MainFunction_Read runs before the runnables so they see this cycle's frames; Com_MainFunctionTx runs after them so their writes leave in the same cycle. Swap them and every reaction is one period late. A real project documents and reviews this order like any other requirement.

21.3The COM stack

Application data travels as signals. Com packs signals into I-PDUs (protocol data units); PduR routes each PDU to the right bus interface; CanIf maps it to a CAN ID and a hardware object; the Can driver puts it in a mailbox. Each layer has its own handle numbers, and the configuration tables connect them.

ModuleKnowsDoes not know
Comsignals, their bit positions, send modes, deadlineswhich bus, which CAN ID

🎭
Analogy

The COM stack is the postal system: a letter (signal) goes into an envelope (I-PDU), the sorting centre (PduR) picks the route, the local post office (CanIf) writes the address (CAN ID), and the truck (Can driver) drives it onto the road (the bus).

21.5The CAN matrix

The CAN matrix (often a DBC file) is the contract between ECUs: every frame's ID, length, cycle time, sender and receivers, and every signal's position, length, byte order, scaling and range. In AUTOSAR it is part of the system description; Com's tables are generated from it. The capstone's matrix (IDs are hypothetical, made up for the course):

21.6EcuM and BswM

The ECU State Manager (AUTOSAR_CP_SWS_ECUStateManager) starts and stops the ECU: it runs the driver initialisation lists, starts the OS, and in a full stack hands over to the BSW Mode Manager (BswM), which switches modes according to rules (communication allowed, sleep requested, …). The capstone uses EcuM-lite: fixed start-up, no shutdown or sleep.

🏭
In production (R4.x)

R4.x projects choose between "fixed" and "flexible" EcuM. With flexible EcuM, most of the start-up after the OS is driven by BswM rules and action lists rather than a fixed callout; communication is started by ComM and CanSM, not by a direct CanIf_SetControllerMode call as here.
