Diagnostics (DCM/DEM, UDS) and NvM

When a lamp fails in the field, someone in a workshop plugs in a tester and asks the car what went wrong. This module covers that conversation: UDS, the diagnostic protocol; DEM, which turns monitor results into trouble codes; DCM, which answers the tester; ISO-TP, which carries long messages over 8-byte CAN frames; and NvM over Fee, which keeps the codes when the power is off.

22.1UDS in one page

🔎
Verification status

Every API, type and rule on this page names its AUTOSAR R25-11 document. The requirement IDs and exact values are still being checked against the R25-11 PDFs; until then they come from the R4.x-era specifications, and no requirement ID is quoted, because the course never makes one up. Progress is tracked in the self-review log.

UDS (Unified Diagnostic Services, ISO 14229-1) is a request/response protocol between a tester and an ECU. Each request starts with a service ID (SID); a positive response echoes SID + 0x40, a negative one is 0x7F, the SID and a negative response code (NRC). The services you meet first:

SIDServiceExample
0x10DiagnosticSessionControl10 03: extended session
0x22ReadDataByIdentifier22 F1 90: read the VIN (DID 0xF190)
0x2EWriteDataByIdentifierwrite a configuration value
0x19ReadDTCInformation19 02 09: DTCs whose status matches mask 0x09
0x14ClearDiagnosticInformation14 FF FF FF: clear all
0x3ETesterPresentkeeps a non-default session alive

⚠️
Debounce before you blame

A monitor that reports FAILED on one bad sample turns every electrical spike into a stored fault and a warranty claim. Report PREFAILED per sample and let Dem count (counter-based) or time (time-based) until the fault is qualified. LampMonitor already judges once per on-phase, so it reports qualified results.

🏭
In production (R4.x)

Older stacks read an event's status with Dem_GetEventStatus; R4.4 introduced Dem_GetEventUdsStatus. Monitors in R4.x projects may also use Dem_ReportErrorStatus for BSW events before Dem is fully initialised.

22.3DCM: request to response

DCM (AUTOSAR_CP_SWS_DiagnosticCommunicationManager) is the ECU's UDS server. It has three sub-layers:

  • DSL (session layer): sessions, timing (P2/P2* server response times), TesterPresent, which connection the request came on.
  • DSD (service dispatcher): is this SID supported in this session and security level? If not, NRC 0x11 or 0x7F.
  • DSP (service processing): the implementation of each service, calling Dem for DTCs, SWCs (through RTE ports) for DIDs, NvM for stored data.

The capstone stops at Dem: DCM-lite and NvM were planned as a stretch goal and are covered here as concepts. The sequence above shows where they would sit.

22.4Transport: ISO-TP on CAN

A UDS response can be far longer than a CAN frame's 8 bytes. ISO-TP (ISO 15765-2, the CanTp module in AUTOSAR) splits it:

Single frame (SF)0 + lengthup to 7 data bytes
First frame (FF)1 + 12-bit lengthstart of a longer message, 6 data bytes
Consecutive frame (CF)2 + sequence number7 data bytes each, numbered 1, 2 … 15, 0 …
Flow control (FC)3 + statusreceiver's reply to an FF: block size and minimum gap

22.5NvM, MemIf, Fee, Fls

Stored DTCs, odometer copies and learned values must survive power-off. AUTOSAR stacks that path in four modules: NvM (blocks with RAM mirrors, CRCs and redundancy) → MemIf (which device) → Fee (Flash EEPROM Emulation) → Fls (the flash driver, the same erase/program work as module 16).

Flash can only be erased in pages, and each page survives about 10 000 erase cycles (DS12288). Fee therefore never rewrites in place: it appends new versions of a block to the active page and, when the page is full, copies the latest version of every block to the other page, then erases the old one. Every step of the cycle must leave a recoverable state: page status markers are written in a fixed order, and at start-up Fee scans both pages to decide which one holds valid data. This is the same reasoning as the bootloader's image record in module 16, applied to data.
