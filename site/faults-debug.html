Fault Handling and Debugging

Sooner or later your program stops in HardFault_Handler, or resets "for no reason". This module turns that from a mystery into a routine: what the Cortex-M3 records when it faults, how to get the faulting instruction back, how to keep the evidence across a reset, and the debugger techniques that find the bug faster than adding prints.

⏱ 45 min read🎯 Intermediate📂 examples/08-iwdg-hardfault

15.1Fault types on Cortex-M3

The Cortex-M3 has four fault exceptions (PM0056 §2.4, ARMv7-M ARM B1.5):

FaultPriorityTypical causes
HardFaultfixed −1 (above every configurable exception)escalated faults, bus error reading the vector table, BKPT without a debugger
MemManageconfigurableMPU violation, executing from an execute-never region
BusFaultconfigurableaccess to an address with no memory or peripheral behind it, a stack running off the end of RAM
UsageFaultconfigurableundefined instruction, ARM-state jump (bit 0 of a function pointer clear), divide by zero and unaligned access if trapping is enabled

After reset the three configurable handlers are disabled. Their faults escalate to HardFault, which then sets HFSR.FORCED. A fault also escalates when its handler cannot run because the code that faulted already runs at the same or a higher priority. A fault inside the HardFault handler itself puts the core into lockup: it stops executing until a reset or the debugger intervenes. Try the paths:

Enabling the handlers in SCB->SHCSR gives each fault its own vector, which is useful in a product (a UsageFault can sometimes be survived; a HardFault rarely). Example 08 keeps them disabled on purpose, so every fault arrives in one handler with FORCED set.

🎭
Analogy

A fault handler is a flight data recorder. It cannot save the flight, but if it records the right things (where, why, which registers), the investigation afterwards takes minutes instead of weeks.

15.2Decoding CFSR and HFSR

Two registers explain almost every fault. CFSR (PM0056 §4.4.14) combines the UsageFault, BusFault and MemManage status bits; HFSR (§4.4.15) says why HardFault was taken. ⚠️
IMPRECISERR: the PC is not the culprit

The Cortex-M3 buffers stores. When a buffered write fails, the core has already moved on, so the stacked PC points somewhere after the bad instruction and BFAR is not valid. While hunting such a bug, set DISDEFWBUF in the auxiliary control register (SCnSCB->ACTLR, ARM DDI 0337 §4.3.1): every store then completes before the next instruction and the error becomes precise. It costs speed, so remove it afterwards.

15.3Recovering the faulting PC

On exception entry the core pushes eight words onto the stack that was in use (PM0056 §2.3.7). The handler can read the faulting program counter from that frame:

OffsetWordWhy you want it
+0x00…+0x0CR0–R3function arguments at the time of the fault (a NULL pointer shows up here)
+0x10R12scratch
+0x14LRwhere the faulting function would have returned to: its caller
+0x18PCthe faulting instruction (for precise faults)
+0x1CxPSRflags; bit 9 says the core inserted a padding word to align the stack

Which stack? The value in LR at handler entry is not a return address but EXC_RETURN; its bit 2 is 0 when the frame is on the main stack (MSP) and 1 when it is on the process stack (PSP, used by RTOS tasks). ⚠️
Keep the handler simple

The fault may have been caused by a corrupted stack or a broken UART driver. A handler that calls into complex code can fault again (and lock up). Copy the registers first, print with the simplest polling code you have, and reset. In a product without a UART, store the record and let the next boot report it.

Debugging a watchdog reset

Example 08 sets DBGMCU_CR.DBG_IWDG_STOP so the watchdog pauses while the core is halted. Without it, every breakpoint held longer than the timeout ends in a reset, and the debugger loses the session (module 13).

15.6printf: UART, semihosting, SWO

Three ways to get text out of the chip:

MethodHow it worksCostOn a Blue Pill
UARTbytes on PA9 to a USB-UART adaptera pin pair and ~87 µs per character at 115200 baud, or a buffer and an interruptthe course's default
Semihostinga BKPT 0xAB instruction; the debugger reads the request and prints on the hostthe CPU halts for every call (milliseconds); no debugger attached means the BKPT ends in a HardFault (HFSR.DEBUGEVT)works with any ST-Link, but never leave it in production code
SWO / ITMthe core's trace unit sends bytes on the TRACESWO pin (PB3) while runningvery low; the CPU does not stopneeds the SWO line to the probe: the original ST-LINK/V2 has it, on most clone dongles it is not wired (check yours)
⚠️
PB3 is a JTAG pin

TRACESWO shares PB3 with JTDO. The course frees PB3/PB4/PA15 with SWJ_CFG = JTAGDISABLE; that keeps SWD but also gives up SWO. If you want SWO, keep PB3 for it and use another pin for your application (module 05).
