Software Components, Ports and the RTE

An AUTOSAR application is a set of software components that never call each other directly. Each one declares ports, implements runnables, and talks through the RTE, a layer generated for each ECU. This module builds the TurnLight capstone's two SWCs from the outside in: components, ports and interfaces, runnables and events, then the RTE API and what the generated code behind it looks like.

A software component (SWC) is a unit of application software with a formal description: its ports, its data types and its internal behaviour. The description is ARXML; the implementation is C.

TypeWhat it doesIn the capstone
Application SWCvehicle function, hardware-independentTurnLight, LampMonitor
Sensor/actuator SWCturns physical signals into application values and back; depends on the ECU's I/Othe job IoHwAb does here, behind client-server ports
Service SWC / ECU abstractionBSW seen through ports (Dem, WdgM, NvM, IoHwAb)Rte_Call_…_SetEventStatus, Rte_Call_Alive_CheckpointReached
Compositiona group of SWCs and their connections, used to structure large systems(not needed for two SWCs)

An atomic SWC cannot be split across ECUs; a composition can. Because SWCs only use their ports, the same TurnLight could move to another ECU: only the RTE and the configuration change.

19.2Ports and interfaces

A port is a typed connection point, provided (P) or required (R). Its interface says what flows through it:

Analogy

The RTE is a switchboard operator. A caller asks for "the lamp" without knowing which extension, building or even city it is in; the operator connects the line. Moving the lamp to another building changes the switchboard, not the caller.

19.3Runnables and RTE events

An SWC's code is a set of runnables: C functions without parameters that the RTE calls when an RTE event fires.

  • Timing event: periodically, for example every 10 ms. Both capstone runnables use one.
  • Init event: once at start-up (RE_TurnLight_Init).
  • Data received event: when new data arrives on a port.
  • Operation invoked event: a server runnable called by a client.
  • Mode switch event, background event, and others.

No hardware in an SWC

The moment an application SWC includes Dio.h or touches GPIOB->IDR, it is tied to one ECU and can no longer be tested against a simulated RTE. tools/check-autosar.py fails the build if an SWC includes anything but its Rte_<Swc>.h, its MemMap header and declared application libraries.

19.4The RTE API

The SWC calls a small set of generated APIs. Their names are built from the port and the data element or operation (AUTOSAR_CP_SWS_RTE):

19.5What generated RTE code looks like

What does the generator produce behind those names? For SWCs on the same ECU and task, a buffer; for data that leaves the ECU, a Com call; for a client-server call to a BSW service, a direct function call. The capstone's RTE is hand-written but follows that pattern:

ℹ️
Why so many tiny functions?

Real generators inline most of them as macros when sender and receiver run in the same task; when they run in different tasks or on different cores, the same API turns into a protected copy or an inter-core transfer. The SWC never notices, which is the point.

19.6A tiny RTE generator

A generator is mechanical: from a port description it derives names, types and the mapping. Try it: describe a port and see the names the RTE would generate for it.

A full generator also creates the task bodies, the data buffers with their protection, the COM callbacks and the VFB trace hooks, all from ARXML. The capstone's rte/ folder shows each of these once, by hand.
