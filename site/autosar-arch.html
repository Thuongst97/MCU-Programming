AUTOSAR Classic: Layered Architecture

Everything so far ran on one chip with code you wrote top to bottom. A car has around a hundred control units from dozens of suppliers, and their software must fit together, move between chips and survive fifteen years of maintenance. AUTOSAR Classic is the industry's answer: a layered architecture, standard module interfaces and a tool-driven method. This module maps it out before the next ones open each layer.

18.1Why AUTOSAR exists

🔎
Verification status

Every API, type and rule on this page names its AUTOSAR R25-11 document. The requirement IDs and exact values are still being checked against the R25-11 PDFs; until then they come from the R4.x-era specifications, and no requirement ID is quoted, because the course never makes one up. Progress is tracked in the self-review log.

Before AUTOSAR, every supplier wrote its own drivers, scheduler and communication code for every chip, and every OEM specified interfaces differently. Moving a function to another ECU or another microcontroller meant rewriting it. AUTOSAR (AUTomotive Open System ARchitecture), founded in 2003 by OEMs and suppliers, standardises the parts that do not differentiate a product so that the parts that do can be reused:

  • Standard basic software (BSW): drivers, communication, diagnostics, memory and mode management with specified APIs, bought from a BSW vendor.
  • Application software components (SWCs) that talk only through a generated layer, the RTE, so they do not know which ECU or chip they run on.
  • A methodology with exchange formats (ARXML) so OEM, supplier and tool vendor work on the same description.

Classic Platform targets deeply embedded ECUs like ours: static configuration, an OSEK-based OS, C code, microcontrollers. Adaptive Platform targets high-performance computers with POSIX, C++ and dynamic deployment. This course covers Classic.

🎭
Analogy

AUTOSAR is the standard shipping container. Any crane (an ECU vendor's basic software) can lift any box (an application component), because the corners and dimensions are fixed. What is inside the box is still the supplier's business.

18.3Methodology and ARXML

A real project does not write the RTE, the configuration tables or the OS task bodies by hand. It describes the system in ARXML (AUTOSAR XML), and tools generate code from that description. Step through the flow:

The ECU configuration is the largest artefact: every module parameter (which pins, which CAN IDs, which signals, which DTCs) is a value in it. Generators turn it into the *_Cfg.h, *_PBcfg.c, *_MemMap.h, Os_Cfg.c and Rte*.c files you will see in the capstone.

18.4Generated vs hand-written

In a production ECU, most files are not written by the ECU's software team. The course labels every file in autosar/ and the capstone with what it would be in production:

⚠️
Never edit generated files

A change made by hand to a generated file disappears at the next generation, usually days later, without anyone noticing. In this repository the same rule holds: files written by tools/gen-autosar-cfg.py or tools/embed-code.py are regenerated, and CI fails when they drift.

18.5Releases and documents

AUTOSAR publishes the Classic Platform yearly (R19-11, R20-11, … R25-11, the release this course cites). Before R19-11 releases were numbered 4.0 to 4.4, and many ECUs in production still run 4.3.1 or 4.4.0. Since R22-11 every document is named AUTOSAR_CP_<type>_<Name>:

TypeContentExample
SWSSoftware Specification of one module: API, behaviour, configurationAUTOSAR_CP_SWS_DIODriver
SRSRequirements on a group of modulesAUTOSAR_CP_SRS_BSWGeneral
EXPExplanatory documentsAUTOSAR_CP_EXP_LayeredSoftwareArchitecture
TPSTemplate specifications (the ARXML meta-model)AUTOSAR_CP_TPS_SoftwareComponentTemplate
TRTechnical reports, such as the module listAUTOSAR_CP_TR_BSWModuleList

Each requirement in an SWS has an ID in square brackets. Reviews and safety cases trace code to these IDs, which is why the course plans to cite them for every rule it teaches.

🏭
In production (R4.x)

ECUs on R4.x use the older document names without the CP_ part (for example AUTOSAR_SWS_DIODriver) and slightly different APIs in several modules. The AUTOSAR pages point out the differences you are likely to meet.

18.6How we do AUTOSAR on a Blue Pill

Real AUTOSAR stacks need licences, configuration tools and a certified OS, and they target automotive microcontrollers. The course builds a small, honest imitation on the Blue Pill so you can read and step through every line:

  • autosar/: MCAL drivers (Mcu, Port, Dio, Pwm, Adc, Wdg, Can) over the STM32F1 registers you know, and "-lite" versions of CanIf, PduR, Com, Dem, WdgM, EcuM, IoHwAb and Det. Each header lists what was left out.
  • autosar/os_shim: an OSEK/AUTOSAR-OS-like API over FreeRTOS. It is not a real AUTOSAR OS, and module 21 lists the differences.
  • capstone/turnlight/stage3-autosar: two SWCs, a hand-written RTE that mirrors generated code, and the configuration files.
